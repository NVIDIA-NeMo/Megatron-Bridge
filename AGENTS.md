# AGENTS.md — Megatron Bridge

> **Project:** PyTorch-native bridge between Hugging Face and Megatron-Core.
> Bidirectional checkpoint conversion, pretraining, SFT, and LoRA recipes
> with optimized NVIDIA GPU performance. Package: `megatron.bridge` (Python 3.12).

## Skills

The `skills/` directory contains structured guides for common tasks (adding
models, running experiments, debugging multi-node jobs, performance tuning,
etc.). **Always read the relevant `SKILL.md` before starting any task it
covers — skills are mandatory context, not optional background reading.**

**Workflow — mandatory order for every task:**
1. **Pull information first.** Read the commit, PR, error log, file, or
   whatever artifact the task is about. Do not reason about it yet.
2. **Select and invoke the skill.** Based on what you just read, identify
   the relevant skill and invoke it before forming any answer or plan.
3. **Answer or implement.** Only after the skill is loaded, use its context
   to reason, diagnose, or write code.

Never skip or reorder these steps. Do not wait for the user to name the right
skill keyword — infer it from the artifact you read.

## Boundaries

**NEVER:**
- Modify files inside `3rdparty/Megatron-LM/` — changes go through the upstream repo
- Run the full test suite — run only the specific tests relevant to your change
- Add required (non-optional) dependencies — use optional extras; submit dependency changes as a separate PR
- Commit secrets, tokens, `.env` files, or environment-specific paths / account names (e.g. `/home/yuya/…`, usernames, cluster hostnames)
- Use bare `print()` — use `logging.getLogger(__name__)` or `print_rank_0()`

**ASK FIRST:**
- Before adding any new dependency to `pyproject.toml`
- Before modifying CI workflows (`.github/workflows/`)
- Before changing public API signatures in `models/conversion/`

**ALWAYS:**
- Run `uv run pre-commit run --all-files` before committing
- Add NVIDIA copyright headers to new Python files (except under `tests/`)
- Sign off commits: `git commit -s -m "message"`
- Use `uv run python -m pytest` and `uv run python -m torch.distributed.run`, not bare `pytest` / `torchrun`
- Use the current year (2026) in generated content — do not default to 2025 or any past year

## Code Style

Lint and format are enforced by pre-commit hooks (ruff). See @ruff.toml for
the authoritative rules. For judgment calls not covered by tooling, see
@skills/linting-and-formatting/SKILL.md. Key points the linter cannot catch:

- Type hints required on all public API functions (`X | None`, not `Optional[X]`)
- Google-style docstrings on public classes and functions
- Use `*` separator for functions with multiple same-type parameters
- No arbitrary defaults for config values — be explicit

## Testing

Run only what your change touches — never the full suite.

```bash
# Single file / single test / keyword match
uv run python -m pytest tests/unit_tests/training/test_checkpointing.py
uv run python -m pytest tests/unit_tests/training/test_checkpointing.py::TestCheckpointUtilities
uv run python -m pytest tests/unit_tests/models/qwen/ -k "moe"

# Multi-GPU functional test (max 2 GPUs)
CUDA_VISIBLE_DEVICES=0,1 uv run python -m torch.distributed.run --nproc_per_node=2 \
  -m pytest tests/functional_tests/test_groups/training/test_pretrain.py
```

Layout: unit tests mirror the package under `tests/unit_tests/<subpackage>/`.
Functional tests are split in two — the pytest files live in
`tests/functional_tests/test_groups/<area>/`, while the CI tier entry points
live in `tests/functional_tests/launch_scripts/<hardware>/{active,flaky}/`
as `L{0,1,2}_Launch_*.sh`. A launch script is a thin wrapper that invokes
`torch.distributed.run` + `pytest` over a set of `test_groups` files with a
`# CI_TIMEOUT=<minutes>` header; adding a functional test usually means adding
the file under `test_groups/` and listing it in the right launch script.
The CI matrix is generated by scanning that directory, so no workflow edit is needed.

`-m "not pleasefixme"` is how CI skips known-broken tests; other markers
(`unit`, `integration`, `docs`, `internal`) are declared in `pyproject.toml`.

- **No foreign `setattr` on config dataclasses in tests.** When a test applies overrides to a recipe config via `setattr(config_obj, key, value)`, always guard with `if not hasattr(config_obj, key): raise ValueError(...)` first. Setting an attribute that does not exist on the dataclass silently creates a phantom field — the test passes but the recipe would fail for a real user who never sets that key. This applies to all override patterns (`model_overrides`, `checkpoint_overrides`, `config_overrides`, etc.) in `tests/functional_tests/`.

## Architecture

Three layers stack on top of each other. Understanding where a change belongs
usually means identifying which layer it is in.

```
recipes/ + perf_recipes/   →  build a ConfigContainer
training/                  →  consume a ConfigContainer, run the loop
models/                    →  providers (build MCore models) + bridges (HF ↔ MCore weights)
```

### Model layer: providers and bridges

A **provider** is a dataclass that subclasses a Megatron-Core
`TransformerConfig` and knows how to instantiate the model:
`GPTModelProvider` (`models/gpt_provider.py`), plus `T5ModelProvider`,
`HybridModelProvider`, `MegatronMIMOProvider`. All implement
`ModelProviderMixin` (`models/model_provider.py`), whose key methods are
`provide()` (single model) and `provide_distributed_model()` (parallelism-aware,
DDP-wrapped). Pre/post-wrap hooks (`register_pre_wrap_hook`) are how PEFT and
similar transformations inject themselves before DDP wrapping.

A **bridge** subclasses `MegatronModelBridge`
(`models/conversion/model_bridge.py`) and is registered by decorator:

```python
@MegatronModelBridge.register_bridge(source=LlamaForCausalLM, target=GPTModel, model_type="llama")
class LlamaBridge(MegatronModelBridge):
    def provider_bridge(self, hf_pretrained) -> GPTModelProvider: ...
    def mapping_registry(self) -> MegatronMappingRegistry: ...
```

`provider_bridge` maps HF config → provider; `mapping_registry` declares
per-parameter name/layout mappings (see `conversion/param_mapping.py` for the
mapping primitives — direct, gated-MLP, QKV, column/row-parallel splits).
`AutoBridge` (`conversion/auto_bridge.py`) dispatches on the HF architecture
string to the registered bridge and is the user-facing entry point
(`import_ckpt`, `export_ckpt`, `save_hf_pretrained`, `to_megatron_provider`).
Weight conversion is streamed as `WeightConversionTask`s, so it is
rank-aware and never materializes the full model on one rank.

Files under `src/megatron/bridge/models/<family>/` are named per model
variant, not per role: `<variant>_bridge.py` holds the bridge subclass and
`<variant>_provider.py` the provider dataclass (e.g. `llama/llama_bridge.py`,
`qwen/qwen3_moe_bridge.py`, `gemma/gemma3_provider.py`). Families with several
variants share helpers via a local `common.py`. HF checkpoint access is shared,
not per-family: `models/hf_pretrained/` wraps HF loading (`causal_lm.py`,
`state.py`).

### Training layer: ConfigContainer

`ConfigContainer` (`training/config.py`) is the single object that fully
describes a run — it aggregates `model` (a provider), `train`, `optimizer`,
`scheduler`, `dataset`, `tokenizer`, `checkpoint`, `logger`, `ddp`, and
optional `peft`, `comm_overlap`, `mixed_precision`, `profiling`, `ft`,
`inprocess_restart`. Most config dataclasses subclass their Megatron-Core or
Megatron-LM counterpart, so adding a knob often means checking whether the
upstream dataclass already has it.

Entry points are `pretrain()` (`training/pretrain.py`) and `finetune()`
(`training/finetune.py`), both taking a `ConfigContainer` plus a forward-step
function (`gpt_step.py`, `vlm_step.py`, `llava_step.py`, …). `training/setup.py`
does the heavy lifting between config and loop: distributed init, model build,
PEFT application, checkpoint load, vocab-size validation. The loop itself is
`training/train.py`.

### Recipe layer

Recipes are functions returning a fully-populated `ConfigContainer`, exported
by name (e.g. `llama32_1b_pretrain_config`) from
`src/megatron/bridge/recipes/<family>/`. Shared skeletons live in
`recipes/common.py` (`_pretrain_common`, `_sft_common`, `_peft_common`, and VLM
variants) — prefer extending those over duplicating a full config.
`src/megatron/bridge/perf_recipes/` holds tuned benchmark configs (named for
their canonical GPU count) and is a separate package from `recipes/`.

### Launchers

- `scripts/training/train.sh` — unified Slurm launcher; selects a recipe via
  `--recipe <exported_name>` or `--model <stem> --mode {pretrain,sft,lora,dora}`,
  with trailing `KEY=VALUE` `ConfigContainer` overrides. See
  `scripts/training/README.md`.
- `scripts/conversion/convert.sh` — checkpoint conversion with CPU or GPU backend.
- `examples/` — standalone runnable scripts per model / feature; the per-model
  READMEs under `examples/models/<family>/` are the best reference for a
  specific model's verified workflow.

### Megatron-Core Submodule

`3rdparty/Megatron-LM/` is a git submodule pinned to a specific commit,
installed as an editable package via `[tool.uv.sources]` in `pyproject.toml`.
Use `scripts/switch_mcore.sh` to switch versions.
